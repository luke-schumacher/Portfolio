Evidence-grounded AI for engineering diagnostics

Doctoral work in cyberphysical systems at FH Aachen, within the ZIM innovation network Smart Green Robotics. The question underneath all of it: how does a system answer a hard engineering question in plain language and prove where the answer came from?

The problem

Race engineers already have the data. They don't have the answer.

A race weekend produces telemetry channels at kilohertz rates, structured session reports, and unstructured driver debriefs — three modalities that describe the same event in incompatible vocabularies. Root-cause analysis today means an engineer holding all three in their head under time pressure.

A language model asked the same question will answer fluently and confidently, and there is no way to tell whether it looked at anything. In an engineering loop, that is worse than no answer.

The approach

Plan the analysis, run it, then answer from the result.

RaceIQ separates language from evidence. A dialogue-capable query planner turns a plain-language question into an executable analysis plan over the fused data and the digital twin. The plan runs. Only then is an answer generated — from what actually came back, with the executed steps attached.

The model chooses what to look at. It does not get to decide what it found.

Themes

Four threads I work along

Multimodal data fusion

Aligning high-rate sensor channels, structured reports and free text onto a single temporal and semantic frame — so a question asked in one modality can be answered with evidence from another.

Digital twins

A queryable model of the physical system that supports counterfactuals — not just "what happened" but "what would have happened at three bar less". Carried over from predictive twin work at Siemens Healthineers.

Verifiable query planning

Turning natural-language engineering questions into analysis plans that are inspectable before they run and auditable after. The evidence trail is a first-class output, not a debugging afterthought.

Neurosymbolic reliability

How multiple specialised agents disagree productively: confidence-weighted consensus, symbolic guardrails on generated reasoning, and honest handling of the case where no agent owns the fault.

What it is

A conversational AI assistant for motorsport engineering. It ingests three unrelated descriptions of the same race weekend — telemetry channels sampled at kilohertz rates, structured session reports, and unstructured driver debriefs — and answers plain-language root-cause questions about them, with the evidence for each answer attached.

The design constraint

An LLM asked "why did we lose two tenths in sector three?" will produce a fluent, confident, entirely unverifiable answer. In an engineering loop that is worse than silence, because it is expensive to check and easy to believe. RaceIQ is built around removing that failure mode rather than mitigating it.

The system separates language from evidence. A dialogue-capable query planner converts the question into an executable analysis plan over the fused data and the digital twin. The plan runs. The answer is then generated from what actually came back — with the executed steps exposed alongside it. The model decides what to look at; it does not decide what it found.

My work packages

Multimodal data fusion — aligning sensor channels, structured records and free text onto a shared temporal and semantic frame, so a question asked in one modality can be answered with evidence drawn from another.

The digital twin — a queryable model of the car and session supporting counterfactuals, not just replay. Direct descendant of the predictive twin work at Siemens Healthineers.

The query planner — plan generation, inspectability before execution, and an audit trail after it. This is the part the doctorate sits on.

Consortium

Delivery is coordinated with Ximaj IT-Solutions (platform engineering), W&S Motorsport (the race team defining ground truth) and Umwelt-Campus Birkenfeld, inside the ZIM innovation network Smart Green Robotics, with Prof. Dr.-Ing. Guido Dartmann (Cyberphysical Systems, FB05).

Where it transfers

Motorsport is a forcing function, not the point. Any domain where high-rate sensor data, written procedure and human testimony have to be reconciled under time pressure has the same shape — clinical operations, industrial plant, grid and charging infrastructure. The evidence-grounding requirement is what makes the work portable.

System architecture

A distributed multi-agent system combining retrieval-augmented generation with Neo4j knowledge graphs for autonomous infrastructure fault diagnosis. Three specialised agents — governance (Telekom policy), hardware (Siemens equipment documentation) and telemetry (Illigo event logs) — coordinate through a RabbitMQ message queue orchestrated by FastAPI microservices. Retrieval runs on ChromaDB with grounded generation on top.

The hard parts

Three heterogeneous sources (PDF, CSV, JSON) updating at different frequencies, with no shared entity vocabulary. Agent coordination that avoids conflicting diagnoses without collapsing the agents into one model. And no ground-truth labels for multi-domain faults, which makes conventional evaluation impossible.

What I built

A unified entity resolution layer with custom parsers — 200 ms of added latency for consistency that everything downstream depends on. A Dempster–Shafer voting mechanism where each agent proposes a diagnosis with a confidence score and a coordinator aggregates probabilistically, so disagreement carries information instead of being averaged away.

And a metric: Mean Time to Innocence — how quickly the system establishes that a fault is not in a given domain. In real operations, ruling a domain out fast is worth as much as naming the culprit, and nothing in the literature was measuring it. Validated against subject-matter experts.

What I'd tell someone starting this

Retrieval quality is the bottleneck, not the model. Roughly 40% of the effort went into chunking strategy and embedding choice, and that was the right allocation. Agent specialisation beat a single larger model consistently — for distributed systems, the division of labour mirrors the domain boundaries that already exist.

Where it transfers

Multi-agent coordination under uncertainty and heterogeneous-source fusion generalise to any operations context where diagnosis spans organisational boundaries. It is the direct ancestor of the RaceIQ query planner.

Technical architecture

A conditional variational autoencoder generating synthetic customer profiles for healthcare technology. PyTorch, dual encoders across 47 demographic and behavioural features, a 128-dimensional latent space, sub-200 ms inference targeting production deployment on AWS EC2 — fed by end-to-end Python/PySpark/SQL pipelines I built alongside it.

Core constraints

GDPR and HIPAA compliance throughout, on severely imbalanced customer segments, with full interpretability required for non-technical stakeholders. In regulated healthcare those are not competing priorities you trade off — they are the shape of the problem.

Solutions and trade-offs

SMOTE oversampling applied in latent space rather than input space, preserving feature correlations that input-space resampling destroys. An attention mechanism in the decoder for feature-importance scoring: 15% slower inference, and the reason the work got stakeholder buy-in at all. INT8 quantisation via TensorRT recovered the loss and then some — 3× speedup for under 2% accuracy cost.

Team and impact

ML engineering lead on a four-person team with two domain experts. Designed the architecture, implemented the training pipeline, and optimised for deployment. Iterative latent-space analysis surfaced customer clusters invisible in the raw data, which went on to inform commercial strategy directly. Recognised with first place at the ITT Summit, with Georg Goertler and Belen Rodriguez.

What stuck

Weekly stakeholder demos prevented late-stage requirement drift — the cheapest process decision on the project. Interpretability treated as a design input from day one, rather than retrofitted, is why the model reached production instead of stalling in review.

Technical stack

A custom Transformer with six encoder layers predicting MRI machine utilisation. It reads a 30-day rolling window of historical usage across 15 engineered features — time of day, weekday, patient priority, procedure type — and outputs a seven-day usage probability distribution per machine. TensorFlow 2.x, served through TF Serving on Kubernetes against a hard sub-50 ms latency budget.

Data and performance constraints

Maintenance windows left irregular gaps in the sampling. Patterns operate at three scales at once — hourly, daily, weekly. Production adoption required beating 85% accuracy, and real-time scheduling required staying under 50 ms on standard hardware. All three at the same time.

Solutions

Time-series-specific imputation: linear interpolation for short gaps, seasonal decomposition for long ones, which preserved temporal structure that naive filling erases. Multi-scale positional encoding to capture short and long cycles simultaneously — 30% more parameters for a 12% accuracy gain. Then knowledge distillation shrank the model 4× while staying within 1% of the original, which is what made the latency budget achievable.

Team and results

ML engineer on a five-person team with two radiologist domain experts. Architecture, training pipeline, ablation studies, production deployment. Final: 89% accuracy, ~15% improvement in resource utilisation.

Key insight

The radiologists surfaced the emergency-case handling pattern that moved the model more than any architectural change did. Transformers excel at long-range dependencies, but positional encoding for time series is a genuinely different problem from positional encoding for language — that assumption cost a fortnight before it broke.

System overview

Automated ESG sentiment analysis over the GDELT Global Events Database — 50,000+ news articles a day. The pipeline runs spaCy entity recognition into VADER sentiment scoring, with Node2Vec graph embeddings over the company mention co-occurrence network. Surfaced through an interactive Streamlit dashboard with NetworkX relationship mapping.

Scale and noise

Most of the corpus is irrelevant, entity extraction produces confident false positives, and generic sentiment models are actively wrong on ESG vocabulary — "greenwashing" and "emissions" do not mean to VADER what they mean to an analyst.

Pragmatic solutions

A 200-term ESG keyword list plus a company whitelist cut noise by 80%, leaving ~10,000 genuinely relevant articles a day. Fine-tuning the VADER lexicon with ESG-specific terms moved sentiment F1 from 0.62 to 0.78. The Node2Vec embeddings turned out to be the interesting part — they surfaced implicit relationships like supply-chain partnerships that nothing in the text stated directly, which became the "related companies" feature.

Team and lessons

ML engineer in a four-person team: NLP pipeline, graph embeddings, dashboard integration. Under 48-hour pressure, simple models with strong features beat complex models with poor data every time — a lesson that has aged well. Graph representations are unreasonably effective at capturing relationships that unstructured text only implies.

Architecture

An interactive platform that teaches prompt engineering through game mechanics. Vanilla JavaScript and HTML5 Canvas on the front end, Groq SDK against Llama-3.1-70B behind it. Five character agents, each with its own system prompt and personality. Client-side state in localStorage, deployed on Netlify with edge functions handling API key security.

Core challenges

Players immediately tried to jailbreak the agents into revealing their system prompts — which is, to be fair, exactly the skill the game teaches. LLM non-determinism made progression unpredictable. API latency of 2–3 seconds broke game flow. And the whole thing had to serve 200+ students on a $50/month budget.

Robustness design

Multi-layer prompt defence: system prompt reinforcement, meta-prompting for jailbreak detection, and graceful fallback responses. A lightweight response classifier validates agent output before it reaches the player, retrying on failure — 60% reduction in variance, at the cost of a little spontaneity. Worth it. Response caching for common interactions plus rate limiting kept it inside budget.

Role and learnings

Technical lead of a three-person student team: agent architecture, LLM integration, game mechanics.

Concise directive prompts consistently outperformed verbose ones — clarity beats length, and it is not close. User testing produced exploits none of us anticipated, which is the argument for adversarial thinking as a default design posture rather than a security phase.
